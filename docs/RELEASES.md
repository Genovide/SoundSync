# Полная сборка и накопительные обновления

Полные сборки Windows и macOS хранятся в релизе `v1.2.0`. Не заменять и не переименовывать эти файлы: установщики используют их адреса и SHA-256 для восстановления основы.

В начале README находятся прямые ссылки на полные сборки и текущий апдейт. Каждый новый релиз обновления также начинается с этих ссылок. Метка Latest принадлежит новому апдейту: проверка обновлений в приложении читает `/releases/latest`.

Новый пользователь устанавливает полную сборку и один последний апдейт. Пользователю установленной версии нужен только последний апдейт. Апдейты включают полный актуальный набор исходников приложения и Python-обработчиков, поэтому установка промежуточных версий не требуется.

## Выпуск апдейта

1. Обновить версию в корневом и app package.json/package-lock.json и целевые версии в .github/workflows/test-upgrade.yml. Обновляторы читают номер из пакета.
2. Добавить docs/releases/<версия>.md и актуальные ссылки в README.
3. Собрать оба ZIP через node scripts/build-upgrades.mjs и проверить scripts/check-update-packages.py. Для Python можно указать SOUNDSYNC_PYTHON.
4. Выполнить форматирование, линтер и подходящие проверки поведения.
5. Закоммитить и отправить исходники. Создать draft-релиз с тегом версии и полным SHA коммита.
6. Запустить workflow test-upgrade.yml с publish=true на этом коммите. Он проверяет апдейты на Windows и Apple Silicon, собирает и проверяет EXE и DMG, затем загружает четыре файла и SHA256SUMS.txt в draft.
7. Дождаться успешного завершения всех заданий, сверить контрольные суммы и опубликовать draft как Latest. Опубликованные версии не перезаписываются.

Нативные проверки описываются как выполненные после успешного завершения соответствующих заданий. Базовые архивы v1.2.0 сохраняют прежние адреса и контрольные суммы.

Полную сборку выпускаем заново при изменении основы, которую нельзя надёжно восстановить существующим установщиком. Тогда обновляем базовые URL и контрольные суммы в установщиках и таблице загрузок.
